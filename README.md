The DriverPass project focused on designing a comprehensive web-based system for DriverPass, a company that provides tools to help students successfully pass their driving exams. The client wanted a centralized platform that combined online practice exams, scheduling for on-the-road training, progress tracking, and administrative management. Their primary goal was to reduce the high failure rate of driving tests by offering structured preparation tools that are realistic, up to date with DMV standards, and accessible online. The system needed to support multiple user roles—students, instructors, administrators, and IT staff—while integrating securely with a DMV API and third-party services such as payment providers and notification systems.

One aspect I believe I did particularly well was aligning the technical requirements with the business needs outlined in the Business Requirements Document (BRD). I ensured that each functional and nonfunctional requirement was reflected in the UML diagrams and technical architecture. For example, role-based access control (RBAC), secure authentication, scheduling workflows, and DMV API integration were consistently represented across the use case, activity, sequence, and class diagrams. I also carefully defined performance, scalability, and security requirements, including HTTPS encryption, JWT authentication, password hashing, and PCI-compliant payment integration. This helped ensure that the design was not only functional but also secure, scalable, and maintainable.

If I were to revise one part of my work, I would improve the UML sequence diagram by adding more detailed error-handling and exception flows. While the main system interactions were clearly modeled, incorporating alternate flows—such as failed payments, API timeouts, or scheduling conflicts—would strengthen the design. Enhancing these diagrams with clearer system boundaries and interaction conditions would improve overall clarity and better reflect real-world system complexity.

When interpreting the user’s needs, I focused on identifying the pain points described in the interview transcript—specifically, the high exam failure rate and lack of structured preparation tools. I translated those needs into measurable system objectives, such as up-to-date practice exams, lesson scheduling, and progress tracking. Considering user needs is critical in system design because software ultimately exists to solve real problems. If a system is technically impressive but does not address user expectations, it fails its purpose. Designing with the user in mind ensures usability, adoption, and long-term success.

My approach to designing software begins with understanding the problem domain and stakeholders. I start by defining clear functional and nonfunctional requirements, then model the system using UML diagrams to visualize behavior, structure, and interactions. I favor a layered architecture to promote scalability and maintainability. In the future, I would continue using structured modeling techniques, stakeholder interviews, iterative prototyping, and risk analysis to refine system requirements. I would also incorporate more user feedback cycles early in the design phase to validate assumptions before implementation. Overall, this project strengthened my ability to connect business needs, system modeling, and technical architecture into a cohesive, user-centered design.
